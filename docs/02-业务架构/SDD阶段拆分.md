# 自建研发平台：SDD 阶段拆分

日期：2026-10-10。状态：阶段拆分草案；未形成经评审的编码计划，未开始新平台实现。

需求基准：[原始需求文档](../01-需求文档/原始需求文档.md)（2026-10-10）。参考研究：[OpenRig 分析](../03-技术架构/OpenRig代码架构与设计分析.md)。研究代码和历史测试不计入新平台进度。

## 1. 执行方式

本项目明确采用 **SDD + Superpowers**。原始需求说明要解决什么问题；阶段规格确定范围、行为和验收；实施计划确定文件、接口、任务和测试；实现证据记录实际结果。四者不互相替代。

每个阶段采用以下顺序，不重新讨论已经确认的技术栈与产品目标：

1. `superpowers:brainstorming`：依据原始需求形成当前阶段规格，只澄清必要差异。
2. 用户评审规格后，`superpowers:writing-plans`：拆成可独立验证的编码任务。
3. 评审计划并确定执行方式后，采用 `superpowers:executing-plans` 或 `superpowers:subagent-driven-development`。
4. 编码按适用的 TDD 技能推进，问题按 systematic-debugging 定位；提交前完成适用的代码审查与 verification-before-completion。

本文件是范围及依赖拆分，不是提前批准全部阶段的实施计划。先细化阶段 0/A，后续阶段在前置证据具备后细化，避免提前猜测 Codex 协议、资源隔离和团队协作方式。

2026-10-10 用户要求按 `dev-project-init` 初始化后整理最终目录：原始需求归入 `docs/01-需求文档/`，本阶段拆分归入 `docs/02-业务架构/`，研究分析和已有阶段 0/A 规格归入 `docs/03-技术架构/`；标准六段入口见 [总索引](../00-总索引.md)。后续阶段规格写入 `docs/superpowers/specs/`，详细实施计划写入 `docs/superpowers/plans/`，实际交付审计归档至 `docs/06-交付审计/`。各正文单点维护，代码目录占位不算实现完成。

## 2. 已确认范围与尚待确认的差异

已确认：中文 WebUI、Vue3/TDesign、FastAPI/SQLAlchemy/MySQL、自有 Python daemon、Codex app-server、资源中央维护、无 OpenRig 运行依赖、轻量实现。2026-10-10 用户确认在当前仓库的 `feature/chinese-multihost-baseline` 分支实现，代码目录为 `frontend/`、`backend/`、`runner/`；旧 OpenRig 工程通过 Git 基准提交追溯，不与新平台并存于工作区，不另建仓库或切换分支。

| 待确认事项 | 当前处理 | 影响范围 |
|---|---|---|
| 独立角色会话或主 agent + 原生 subagent | 原始需求采用前者，后续讨论提出后者；两者尚未合并为已确认决定 | 不阻塞单会话基础规格；团队实现前必须决定 |
| 试点项目和可迁移 SOP 来源 | 可先用不含真实数据的测试资源；正式迁移需要实际来源 | 阶段 D 迁移验收 |
| 隔离登录与真实 Codex 测试环境 | 只在隔离目录验证，不复制 HOME、凭证或修改日用配置 | 阶段 A 真实运行验证 |

“使用 Superpowers”是开发本平台的方法；“平台调用 Codex subagent”是产品的运行方式；“使用子 agent 来实现本项目”是本次开发的执行方式。三者分别决定，不能互相推导。

阶段 B 只做完成真实闭环所需的页面。阶段 C 补齐其中文交互和运行状态，D 再增加团队与 SOP 页面；F 完成其余能力。不是 B/C 就承诺完整产品页面。

### 阶段 0/A：先验证执行基础

按依赖顺序拆成六个工作包，详细任务需在规格评审后编写：

1. **隔离环境与版本基线**：在当前分支建立 `runner/` 的独立 uv 环境、可丢弃测试 Git 项目和测试状态目录；记录本机版本与协议来源，不使用日用项目做实验。
2. **协议与一次执行**：初始化、创建 thread、启动 turn、关联响应与事件、正常退出和错误结束。
3. **环境准备**：来源及版本清单、目录与 Git 检查、所需资源投放、用户修改冲突、实际加载验证。
4. **权限审批与停止**：原生审批接受/拒绝/失效、重复决定、停止及子进程收尾。
5. **执行去重与恢复核对**：本地记录、执行 ID 去重、工作区占用、崩溃未知窗口、磁盘失败、显式恢复。
6. **真实验收与能力结论**：依次运行正常链路和故障场景，产出事实、限制及对阶段 B 的接口约束。

不在此阶段建设管理网页、MySQL 任务 API、团队调度器或 SOP 编辑器。真实验证使用开发测试入口，不将该入口变成面向用户的 CLI 产品。

### 阶段 B：单节点纵向闭环

分为三个可独立验收的切片：

- **B1 任务闭环**：前后端及 MySQL 部署，节点登记和项目工作区映射，网页启动一次真实只读任务并查看结果。
- **B2 人工控制**：权限请求显示与决定回传、停止指令、活请求身份核对；浏览器不持有节点凭证。
- **B3 断连与重开**：事件先落盘后上传、服务端去重、已接收与已处理分开显示、网页重开不新建执行、节点离线不自动转派。

MySQL 原子领取和节点 SQLite 去重分别测试，不能用 SQLite 替代中央数据库集成测试。中央用户访问控制和节点凭证范围在 B 的规格中明确，不能以单用户为由省略控制入口的授权。

### 阶段 D/F：SOP 迁移覆盖

| 来源 | 首次交付阶段 | 核心验收 |
|---|---|---|
| dev-start、dev-eod | D | 加载正确上下文；保存状态、经验与交接；无已授权任务时不自行开工 |
| dev-project-init | F | 项目和模板建立，已有文件不覆盖 |
| dev-decide | F | 候选、选择、原因、影响与复评条件可查 |
| dev-bug | F | 记录已发生根因与修复，不误变成自动修复入口 |
| dev-review | F | 按项目规范审查，明确与通用审查分工 |
| dev-commit | F | 只提交授权范围内文件，不自动 push、不提交无关变更 |
| dev-delivery-check | F | spec/plan/code/文档一致；验收与 tag 授权分开 |
| dev-recall | F | 仅检索已迁移且有权访问的内容，注明范围和出处 |
| dev-sort-inbox | F | 预览分流，明确确认后才清空 |

D 的导入和交付基础能力不算上述 F 阶段 SOP 已完整迁移。每项还需与真实旧资产逐项比对授权和副作用。
