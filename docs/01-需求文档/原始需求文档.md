## 1. 目标与完成标准

用户从一个中文网页完成：接入项目 → 使用标准团队 → 选择平台 SOP → 确认执行安排 → 启动 → 查看进度／处理人工确认 → 审查交付结果。

先确定团队职责与 SOP，再确认执行电脑；默认带出项目已配置的电脑，允许修改。接入本地项目需要读取代码时，可先指定“项目所在电脑”，但不据此绑定后续全部任务。首版一个项目团队在一台电脑执行，随后验证跨电脑交接。

最终验收同时满足：

1. Vue3 WebUI 是唯一产品管理入口，项目、节点、团队、SOP、配置、审批、恢复和交付审查在网页完成。
2. FastAPI 平台与前端独立构建部署；执行电脑运行自有 Python daemon，通过 Codex app-server 完成实际工作。
3. Mac 首节点完成真实任务；Linux 第二节点对指定 commit 独立验证，报告引用一致的代码与规范版本。
4. 三至四个项目可以处于不同阶段；目录、角色会话、任务、审批和成果各有明确归属，同机也不混淆上下文。
5. 既有 10 个 dev-* SOP 的业务能力、资料和适用规则迁入平台，旧名称只供追溯，不保留长期 Vault 结构、旧命令或双仓依赖。
6. 原授权约定逐项映射为平台规则，明确沿用、调整或废止；不因迁移、选团队或启动任务默认扩大权限。
7. 区分执行中、待确认、失败、中断、连接不可达、结果待核对、任务完成、验证通过与用户验收；进程存活不代表交付成功。
8. 新平台不依赖 OpenRig daemon、Node.js 执行服务、CLI、TUI、React UI 或其数据库；Codex 与项目开发工具仍是执行所需组件。

前端构建可能使用 Node.js，项目自身也可能需要 Node.js；本方案取消的是 OpenRig Node.js 执行层，不是禁止任何工具使用 Node.js。

“全中文”覆盖操作与理解层。代码、协议字段、地址、用户命名和原始诊断保留原样；账户登录、操作系统授权等外部确认提供中文说明与准确入口，由用户完成。日常管理不要求手敲命令，不用网页里的命令行替代管理界面。

本方案承接 KPerson 路线图 V0.1–V0.3 的相关目标，不自动修改总体排期、扩大到 V0.4/V0.5 或授权真实发布。LangChain/LangGraph 与协调 agent 仅列为待验证选项，见第 11 节。

## 3. 技术栈、部署与职责

| 层次 | 技术 | 职责 |
|---|---|---|
| 前端 | Vue3、TypeScript、Vite、Pinia、Vue Router | 页面、交互与前端状态；Composition API + script setup |
| 组件与样式 | tdesign-vue-next、Tailwind CSS | 优先现成组件；布局用工具类，组件内部主题用 TDesign 变量，不用深度选择器覆盖 |
| 平台后端 | Python、FastAPI、SQLAlchemy | 项目、团队、SOP、资料、审批、节点登记、任务派发与交付记录 |
| 平台数据库 | MySQL | 中央业务记录与待领取任务，模型与迁移纳入版本控制 |
| 执行节点 | Python、asyncio、sqlite3 | 常驻执行服务、Codex 子进程、任务去重、事件记录与恢复核对 |
| AI 执行 | Codex app-server、Git、项目工具链 | agent 执行、工具调用与会话历史 |
| 通信 | HTTPS 短请求轮询；本地 stdio | 节点主动领取/上报，Python 本地驱动 Codex；首版无跨机 WebSocket |
| 环境与部署 | uv、独立 .venv、Docker Compose、launchd/systemd | 锁定 Python 依赖；中央容器部署，节点由操作系统托管 |

中央先保持一个 FastAPI 应用，Compose 分别部署前端静态服务、后端和 MySQL。前后端分离不要求跨域，可由统一入口提供网页和 API。Mac 首节点、Linux 第二节点；中央可先在 Mac Docker 验证，再部署到 Linux。

中央不运行 Codex，节点不运行 MySQL 或完整平台后端。节点主动访问平台，不开放入站管理端口。节点凭证只允许领取自己的任务和提交对应执行信息；浏览器只访问平台，不能直接控制节点或持有节点凭证。

中央资料与 SOP 是权威来源；实际运行状态来自节点报告。平台离线或节点不可达时展示最后报告时间，不把缓存状态当作实时事实。不跨电脑共享 SQLite，不直接读写 Codex 内部数据库，不复制整份 HOME 或个人配置。

Node.js/Hono、tmux、OpenRig 队列和恢复机制仅是历史研究对象，不迁入运行链路。Codex 协议与生命周期由首轮验证确认，不能把旧 OpenRig 的行为视为新实现自动拥有的能力。

## 4. 轻量 Python 执行引擎

### 4.1 方案比较与选择

| 方式 | 好处 | 成本与判断 |
|---|---|---|
| Python 常驻服务 + HTTP 轮询 + 本地 SQLite | 无节点入站端口，无消息中间件，断连后容易继续上报 | 有轮询延迟；推荐作为首版 |
| Python 常驻服务 + WebSocket 长连接 | 指令与事件延迟低 | 仍需处理确认、重传和本地持久化；出现实际延迟问题后再考虑 |
| Celery/Redis 或通用流程框架 | 提供通用任务分发能力 | 不能替代 Codex 会话与审批管理，当前增加部署成本，不采用 |

HTTP 轮询先使用普通短请求，不引入长轮询框架。任务领取和控制指令分开轮询：执行槽位满时停止领取新任务，但必须继续收取停止与审批指令。首版轮询间隔可先用固定实现值，通过真实任务验证后再决定是否需要配置。

### 4.2 最小结构

```text
Vue3 WebUI
    ↕ HTTP，页面按需刷新
FastAPI + MySQL
    ↕ 节点主动发起 HTTPS 请求：领取、事件、审批结果、状态
Python 执行 daemon（一个常驻进程）
    ├─ asyncio：通信、Codex 子进程、事件读取
    ├─ sqlite3：执行关联、待上报记录、已接收指令
    └─ Codex app-server（每次独立执行一个子进程）
           ↕ 本地 stdio
        项目工作区、Git、开发工具
```

节点不再部署 FastAPI、MySQL 或独立队列服务。SQLite 用 Python 标准库访问，只记录恢复和重传所需数据，不能代替中央项目资料库。标准库负责 asyncio、子进程、JSON、SQLite；HTTPS 客户端实施时选择一个已有或必要依赖，不手写网络协议。

Python 以前台常驻方式运行，由 Mac 的 launchd 或 Linux 的 systemd 托管；不自行 fork 到后台，不依赖 tmux。服务停止与异常退出的子进程清理必须在两种系统实测，不能仅凭服务管理器配置推断无残留。

daemon 是执行服务，不是 LLM agent。团队角色和 SOP 由平台定义，节点只执行明确任务。首版按需启动角色，不为每个角色常驻一个进程；不同角色使用独立会话，通过任务说明、commit 和交付证据交接。

### 4.3 Codex 接入与任务边界

采用 Codex app-server 的本地 stdio JSON 协议。Python 启动子进程，完成初始化，创建或恢复 thread，启动 turn，持续读取事件，并响应原生审批请求。无需从终端文字或 tmux 画面推断状态。

首版将一次执行限定为一个 Codex turn；turn 内部可以包含多轮模型与工具调用。用户继续对话或进入下一步时创建新的执行记录，可显式恢复同一角色的 thread。turn 完成后收尾并退出对应 app-server 子进程，下一次执行按已记录 thread 恢复。是否能按预期加载现有 rules、skills、hooks，必须用所选 Codex 版本验证。

平台负责分配唯一执行 ID、项目、角色、节点、工作区映射、任务输入和上下文版本。节点验证工作区，再在本地记录接收结果，之后才启动 Codex。记录平台执行 ID 与 Codex thread/turn 的映射；收到重复执行 ID 时返回已有记录，不再启动一个进程。

节点执行并发使用显式上限，按电脑容量设置；不自动扩容。相同工作目录同一时间只允许一个写入任务，其余任务留在中央等待；需要并行改同一仓库时显式准备不同 worktree。等待审批仍占用该工作区，防止其他任务改动审批依据。

节点启动前必须完成第 5.1 节的环境准备并记录结果。至少能区分“已接收”“准备中”“执行中”“等待人工”和执行终态；具体字段在 SDD 中确定，不照搬 OpenRig 全部状态。必需资源准备失败时返回缺失项或冲突原因，不启动任务后再宣称配置齐备。

### 4.4 平台与节点各自保存什么

| 位置 | 保存内容 |
|---|---|
| 中央 MySQL | 项目、团队/SOP、资料版本、节点工作区映射、任务与执行 ID、审批决定、收到的进度和结果 |
| 节点 SQLite | 已接收执行 ID、工作区、资源准备结果与上下文版本、thread/turn 标识、执行结果、待上报事件、已处理控制指令 |
| Codex 本机状态 | Codex 自己维护的 thread 历史与配置；通过接口访问，不读取其内部数据库 |
| 节点本地安全配置 | 平台连接凭证与 Codex 登录；不进入任务记录、日志或 Git |

节点中的“已接收”记录在平台仍可能重试该执行期间保留，不能随着进度事件清理一起删除。连续文本输出按小段合并落盘和上传，避免每个 token 写一条记录；已确认的过程事件可以清理，最终结果和执行关联保留到明确归档。

平台运行状态来自节点报告，离线时展示“不可达、最后报告时间和已知状态”，不推断任务已经停止。节点不保存另一份可独立编辑的 SOP 或项目知识库。

### 4.5 传递、审批与恢复

采用至少一次传递加去重，不承诺跨进程的严格恰好一次执行。平台领取操作在 MySQL 中原子绑定执行与指定节点；连接超时或心跳丢失不自动把同一执行交给另一节点。

节点事件带执行 ID 和递增序号，先持久化再上传；平台按这两个值去重，落库后确认。节点重连后继续发送未确认记录。停止、审批等控制指令同样带唯一 ID，重复请求不能再次生效。

Codex 运行时权限审批绑定执行 ID、thread/turn、当前 app-server 进程实例及原生请求 ID。网页展示真实操作和可选决定，节点将决定回传给对应的活请求。已有授权按范围沿用，平台不因启动任务而扩大 Codex 权限；执行完成、请求失效或进程重启后，旧权限审批作废。

SOP 中的需求确认、方案选择和交付验收属于业务决策，绑定项目、任务及对应阶段或产物版本；不能复用运行时权限请求来表达，也不能因进程退出自动删除已经形成的业务决定。待处理页面可以统一展示，但要明确事项类型、作用对象和决定结果。重复点击不能重复推进步骤；批准方案不等于允许任意工具操作，批准工具操作也不等于用户验收交付。

| 情况 | 首版行为 |
|---|---|
| 关闭网页 | 不停止节点上的执行 |
| 中央断连 | 已有 Codex 任务继续，本地暂存事件；遇到人工确认则等待，不自动批准 |
| 重复派发 | 相同执行 ID 返回现有结果或状态，不再次启动 |
| Codex 进程失败 | 上报失败和已产生结果；不自动从头重跑 |
| Python daemon/电脑重启 | 核对遗留进程、执行记录及 Codex 历史；未完成执行标记中断或结果待核对，显式恢复时创建新执行并关联旧记录 |
| 启动前后崩溃，无法确定是否已执行 | 标记结果待核对，不凭缺少 thread ID 自动重新启动 |
| 用户要求停止 | 向当前 turn 发中断请求并核对结果；必要时终止该执行的子进程，不影响其他项目 |
| 磁盘写入失败 | 停止接新任务并报告错误；无法记录在途结果时中断受影响执行，不宣称完成 |

断连期间事件记录按实际需要设置本地容量上限，达到上限时停止新增执行并中断无法继续可靠记录的任务，不能无限增长或默默丢失审批与结果。具体数值在真实输出样本验证后确定，不预建日志平台。

“恢复 thread”是继续会话，不等于恢复崩溃前那条系统命令。恢复前必须核对工作区变更与未完成步骤。若发现仍运行的旧进程，先识别并停止或核对它，再启动新进程；仅凭 PID 不判断身份。

## 5. 项目上下文、配置与团队

### 5.1 权威来源与加载

| 资产 | 权威来源 | 加载与维护规则 |
|---|---|---|
| 代码与技术文档 | 项目 Git 仓库 | 节点工作区/worktree；任务记录分支、起始 commit 和交付 commit |
| 项目规则 | 项目 AGENTS.md 与平台适用规范 | 项目 > 适用的项目组规范 > 全局；迁移时显式读取 CLAUDE.md/Vault 规则并确认范围 |
| 状态摘要、决策、bug、经验 | 平台项目记录 | 从 Vault 导入并保留来源；与项目已有 PROGRESS/MEMORY 明确分工 |
| 通用规范与 SOP | 平台版本化资产 | 初始从 KPerson 迁入，按项目、角色和任务加载，不全量注入每段对话 |
| 团队与角色 | 平台标准团队模板 | 每项目创建独立团队实例，按阶段启用角色 |
| Codex agents、skills、插件 | 选定资产与原安装渠道 | 复核现有角色，按需加载；不将插件缓存当安装包，不复制整套角色 |
| hooks/MCP | 受管理资产 + 本机安装配置 | 节点解析路径与解释器，沿用明确的信任约定 |
| 凭证与登录 | 系统安全存储或受保护且忽略提交的本机配置 | 不进入 Git、镜像、任务记录或日志 |
| 对话与交接 | Codex 会话 + 平台任务与交付记录 | 传递目标、commit、规范版本、证据和下一步，不共享所有聊天 |

平台保存项目与节点工作区映射；节点核对目录、Git 根与适用规则。每次执行绑定项目、角色、工作区、上下文版本及 Codex thread。新项目不复用旧项目 thread，不能靠一个共享聊天窗口区分多个项目。独立目录和会话是操作与上下文隔离，不声称构成操作系统安全沙箱。

资产安装先核对来源与版本、预览差异并备份，再合并受管理部分；不覆盖整份 config.toml、hooks 配置或项目 AGENTS.md。文件存在不证明已加载，必须用真实 Codex 任务验证。KPerson 安装逻辑可供参考，迁入资产不再在两处独立演进。

每次执行的最小环境准备顺序：

1. 领取绑定了项目、角色、SOP 及资源版本的任务，核对节点工作区和 Git 状态。
2. 解析本次需要的项目规则、角色指导、skills、hooks、MCP 与配置，保留来源、版本和适用范围；本机路径与解释器由节点解析。
3. 只准备所需资源，记录实际落地内容及与预期的差异；必需资源缺失、配置冲突或未满足既有信任条件时，说明原因并停止进入执行。
4. 保存准备结果后启动 Codex，关联 thread/turn，并按已验证的能力完成加载检查；无法确认的项目标记“未验证”，不伪报生效。

中央维护资源定义、内容或版本化引用；节点保留工作树、执行所需文件和可重建缓存。Git 负责代码传递，平台负责 SOP、规范和任务记录，不把代码工作树全部存入 MySQL。缓存不能成为另一份可独立编辑的权威资产。

验证分别记录“文件已准备”“运行时已加载”“任务实际调用”“调用结果”。只有任务要求使用的能力才验证实际调用，不要求每次执行调用全部技能。任务依赖的 MCP 必须有可达性或实际调用证据，不能以配置存在替代；OpenRig 的管理 MCP 与任务所需外部 MCP 也不能混为一项依赖。

资源所有权保持明确：平台生成内容只更新自己管理的部分，发现用户修改时报告差异，不复制 OpenRig 缺少历史 manifest 时仍可能覆盖的行为。项目工作目录、角色 thread 与运行时配置隔离分别验证；独立 `CODEX_HOME` 仅是候选方案，须核对登录、MCP、插件、hooks 与 thread 恢复，不能仅设置环境变量就宣布隔离完成。首版使用普通文件准备函数，不预建通用资源打包或插件框架。

### 5.2 迁移与单一写入来源

按项目执行：盘点旧内容与规则 → 导入平台并记录来源/版本 → 核对完整性、适用范围与授权映射 → 切换主写入来源。导入失败不切换；切换后旧 Vault 只作历史归档，不长期双写或双向同步。

平台检索只覆盖已迁移且有权访问的资料，并展示范围和出处；不能把项目子集冒充完整旧 Vault 检索。迁移后的知识写入和检索不依赖 Mac 在线。

### 5.3 标准团队与多项目

| 角色 | 职责 | 启用时机 |
|---|---|---|
| 产品 | 需求、范围、验收与决策 | 梳理需求 |
| 开发 | 实现与必要验证 | 开发阶段 |
| 测试 | 对指定 commit 独立验证并记录证据 | 有待验证产物 |
| 运维 | 部署检查与发布准备 | 发布阶段，真实发布遵循明确授权 |

模板是可复用定义，项目团队是职责组合，角色会话是实际执行上下文，三者不能混同。首版不复刻 OpenRig 的 Rig/Pod/Seat 层级，只保留当前项目与角色需要的信息。

先单项目闭环，再两项目、三至四项目并行；按电脑容量与账户额度启动任务，不常驻十六个 agent。角色之间通过明确任务与证据交接。第二电脑验证时检出指定 commit，未 push 的本地提交不假定远端可见；Git 传递代码遵循已有授权。

## 6. 中文项目入口与 SOP 迁移

首页展示项目名称、执行电脑、当前任务、需处理事项和 SOP；团队详情和原始执行事件放详情。这是产品交互改造，与纯翻译分开提交。首版不提供网页终端；日常操作、审批和故障说明均通过明确网页入口完成。

以下 10 项是迁移覆盖清单，旧命令名仅用于追溯，不是平台必须长期保留的接口。平台承接业务目的，按网页工作流调整步骤；不要求永久维持十个独立按钮或旧 Vault 组织方式。

| 来源 SOP | 平台中文入口 | 迁移后的业务要求 |
|---|---|---|
| `dev-project-init` | 初始化项目 | 工作区、文档模板、阶段、平台项目登记；已有文件不覆盖 |
| `dev-start` | 开始工作 | 检查代码仓库，加载平台规则、最近决策、阶段和任务上下文；无已授权任务时等用户指令，不再要求双仓同步 |
| `dev-decide` | 记录决策 | 候选、选择、原因、影响、重新评估条件 |
| `dev-bug` | 记录已修复问题 | 已发生根因与修复，不是自动修 bug |
| `dev-review` | 项目规范审查 | 平台管理的反模式与项目规则，明确与 gstack 通用审查的分工 |
| `dev-commit` | 提交变更 | 检查代码 diff，按平台授权提交；项目记录写入平台，不再提交 Vault；不自动 push，不用 git add . 收无关变更 |
| `dev-eod` | 收工与交接 | 状态、经验、明日事项、提交/交付提醒 |
| `dev-delivery-check` | 交付一致性检查 | 按阶段核对 spec/plan/code/文档；用户验收与 tag 操作按平台授权分别处理 |
| `dev-recall` | 查找历史经验 | 检索平台已迁移且有权访问的知识，给范围、来源和结论 |
| `dev-sort-inbox` | 整理速记 | 整理平台收件箱，先展示分流，确认后才清空 |

选择 SOP 时绑定项目、团队、SOP 版本和任务输入，确认执行安排后再绑定主机与工作目录。首版采用预置流程，不做流程编辑器或任意 shell 按钮。先验收“开始工作／收工与交接”，再覆盖其余业务能力。授权由平台明确展示并记录，已有有效授权按范围沿用；提交、push、tag、发布及清空记录分别明确，不把选团队、选电脑或启动流程当作全部动作的授权。

## 7. 中文 WebUI 与交互边界

采用 Vue 前端，不继续汉化或照搬原 React 页面。首批页面包括项目概览、接入项目、标准团队、SOP 选择、执行安排、任务详情、待确认事项、交付审查、节点与设置；随后补资料、规范、历史经验和收件箱。

保留中英文切换需求，国际化库与版本在前端初始化时核对后确定。使用稳定语义键；显式选择优先于浏览器语言，中文浏览器首次中文，其他语言回退英文，保存用户选择。验证语言键、插值、日期、数字、页面标题和无障碍标签。错误按原错误码处理，中文解释之外允许展开原始诊断。

| 概念 | 中文显示与边界 |
|---|---|
| 项目、团队、角色、会话 | 分别表达业务归属、职责组合、职责与 Codex 上下文 |
| 任务、执行、turn | 用户目标可包含多次执行；首版一次执行对应一个 Codex turn |
| 需要处理 | 区分业务决策、运行时权限请求、补充输入与故障，显示对应原因和处理入口 |
| 已接收、准备中、运行时就绪 | 分别表示任务已登记、环境正在准备、运行时可交互；均不代表 SOP 已完成 |
| 空闲 | 表示当前无活动，不能替代任务完成或交付验收 |
| 恢复会话、新建会话 | 明确是否延续 thread 历史；均不代表自动恢复原系统命令 |
| 节点在线、任务完成、验证通过、用户验收 | 独立展示，不合并为一个绿色状态 |

代码、路径、模型名、协议字段、用户命名和日志保持原样，不翻译 Codex 协议数据流。审批页展示真实操作、项目、工作区与可选决定，不用中文包装隐藏实际授权范围；语言切换不构成授权。

使用支持中文的字体回退，验证 TDesign 组件、长文案、换行、深浅主题、1440/1024/窄屏、缩放及键盘操作。中文输入法确认、粘贴路径、一次提交与页面重连必须在真实浏览器测试。

首版通过执行事件展示过程，不要求终端模拟器、WebSocket 中转或用户学习 tmux。登录与操作系统授权若必须在本机完成，提供中文引导与状态反馈；平台不能替用户默默授权。

项目和节点的页面选择只是浏览范围，不能改写正在执行任务的目标；提交操作时使用该任务绑定的项目、节点、执行及请求身份。多个页签切换后不得显示为新目标的旧缓存结果。页面分别反馈指令已接收、节点已处理及最终结果；停止或审批请求返回成功不直接显示任务完成。语言转换只作用于展示和明确编写的中文指导，不修改机器状态码或原始协议。

## 8. 统一实施顺序与阶段验收

以下 0/A–F 是自建平台的新顺序，旧 React 汉化和 OpenRig 改造阶段不再适用。第 2 节历史记录仅作参考；所有新平台阶段均未完成。

### 阶段 0：环境与最小业务输入

- [ ] 在当前仓库和分支落实新平台目录、版本记录与依赖锁定方式；Python 用 uv 管理兼容版本和独立 .venv，不修改全局 Python/Node。
- [ ] 准备可丢弃项目、Vault 迁移样本、隔离 MySQL 与节点状态目录，盘点 SOP、规则、skills、hooks 的来源版本和授权约定。
- [ ] 测试与日用 Codex 的配置、会话和工作区隔离；只清理测试创建的资源，不重启日用 OpenRig/kernel。
- [ ] 核对 Docker、Mac/Linux 工具链、节点访问中央的网络与账户条件，不默认公网暴露。

验收：能够说明代码、数据、登录与规则来自哪里，测试不会写入真实项目或日用状态。

### 阶段 A：本机 Python → Codex 协议验证

- [ ] Python 驱动 app-server 初始化、thread 创建/恢复、turn 启动、事件读取与停止。
- [ ] 实测审批接受、拒绝、过期，核对规则与 skills/hooks 的实际加载。
- [ ] 验证资源准备、用户文件冲突、必需资源缺失及所需 MCP 调用；记录实际配置来源，核对候选 CODEX_HOME 隔离与 thread 恢复。
- [ ] 验证 turn 收尾、子进程退出和下一次执行恢复 thread；记录不支持或行为不同的功能。
- [ ] 覆盖启动窗口崩溃、重复执行 ID、磁盘写入失败与 daemon 重启。

验收：真实 Codex 的执行、审批、停止、恢复闭环有证据；模拟协议测试不能替代。A 未通过不扩展平台页面或团队编排。

### 阶段 B：中央平台与单节点网页闭环

- [ ] Vue、FastAPI、MySQL 独立构建部署；Python 节点主动领取任务和上报事件，无节点入站端口。
- [ ] 建立节点登记、项目工作区映射、唯一执行 ID、事件去重和网页任务详情。
- [ ] 网页发起真实只读任务，完成一次审批；关闭/重开页面回到同一执行。
- [ ] 验证中央断连、控制指令轮询、结果未知时核对、不重复派发和过期审批拒绝。
- [ ] 在中央容器网页到 Mac 真节点链路中，分别核对查看状态、启动、权限审批、停止和结果返回；网页操作成功提示与节点实测一致。

验收：Vue → FastAPI/MySQL → Python daemon → Codex 往返可核对，不依赖 OpenRig、CLI/TUI 或网页终端。

### 阶段 C：中文主路径与状态可信

- [ ] 完成第 7 节主路径和权限、登录、恢复说明。
- [ ] 区分节点不可达、执行中断、结果待核对、完成与验收，显示状态来源和更新时间。
- [ ] 真实浏览器验证中文输入、语言切换、布局、多个页签和项目切换。
- [ ] Mac launchd 托管验证；关闭网页、停止任务、停止 daemon 的含义清楚。

验收：指定日常路径无需手敲命令，agent 计划、回复与报告默认中文，不用历史输出证明进程仍在运行。

### 阶段 D：项目、标准团队与首轮 SOP

- [ ] 先选团队和 SOP，再确认执行电脑；运行绑定正确项目与工作区。
- [ ] 迁移试点资料和“开始工作／收工与交接”，由平台写入状态摘要、决策和经验。
- [ ] 角色按阶段执行，使用独立会话和明确交接，不引入通用自动调度。
