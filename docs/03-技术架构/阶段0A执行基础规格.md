# 阶段 0/A：Python 执行基础规格

日期：2026-10-10。状态：**规格草案，待用户评审**。尚无产品实现或真实运行通过结论。

来源：[原始需求](../01-需求文档/原始需求文档.md)第 3–5、8–11 节；阶段定位：[SDD 阶段拆分](../02-业务架构/SDD阶段拆分.md)。本规格只细化执行基础，不修改已确认的产品范围。

## 1. 目标与范围

在隔离 Mac 测试环境，用 Python 驱动选定版本的 Codex app-server，完成一次执行、资源准备、权限确认、停止、thread 恢复和失败后的状态核对，并提供阶段 B 可以依赖的证据。

实现采用普通 Python 模块和必要的有状态对象。第一阶段仅有 Codex 一个运行时，不创建插件式执行器、通用流程框架或 OpenRig 兼容层。

本阶段不实现中央 HTTP API、MySQL、Vue 页面、跨机分派、完整 SOP 迁移、系统服务安装及自动升级；这些分别进入后续阶段。也不在未验证前把“一次执行一个 app-server、一个 turn”和独立 CODEX_HOME 宣布为已确定可行的生产方案。

## 2. 方案与选择依据

| 方案 | 取舍 |
|---|---|
| 先做单会话执行核心，再做网页闭环（推荐） | 直接检验原需求最关键的外部依赖，避免接口和页面建立在错误假设上 |
| 先搭全套前后端骨架 | 容易得到可演示页面，但未解决实际执行、审批与隔离问题，暂不选 |
| 先做团队/subagent 调度 | 依赖基本协议、配置和会话能力，还存在需求差异，暂不选 |

阶段 A 的基础实验不决定团队模型。原生 subagent 和独立角色会话的选择，另依据用户决定及必要能力验证落实，不能以本阶段的单会话测试代替。

2026-10-10 的只读探测观察到本机 `codex-cli 0.162.0`、`uv 0.11.16`，`codex app-server --help` 提供 stdio 和协议 schema 生成入口，且标有 experimental。命令返回 0，但提示 PATH aliases 创建受权限限制；没有启动 app-server、调用模型、检查登录或验证隔离。该记录只是当前观察，执行时重新记录并锁定实际版本。

## 3. 环境与资源边界

**S-A01 隔离环境。** 按用户 2026-10-10 的决定，新代码进入当前仓库 `feature/chinese-multihost-baseline` 分支的 `runner/`，不另建仓库或切换分支。原 OpenRig 工程已从工作区退出，按固定 Git 提交追溯，不操作日用 OpenRig 进程。前后端分别进入 `frontend/` 和 `backend/`，当前三个目录只有占位文件。使用 uv 管理的兼容 Python、独立 `.venv` 和锁文件；Python 版本在创建工程时结合依赖约束选定。测试 Git 仓库、资源和状态目录均可丢弃，清理仅作用于本轮创建且记录的目录，不拿新平台自身工作树做执行实验。

**S-A02 配置与身份。** 不复制 HOME、不修改日用 Codex 配置、不读取 Codex 内部数据库。测试凭证通过明确的受保护方式取得，不进入 Git、日志、报告或测试夹具。无法建立隔离登录时只执行模拟验证，真实验收明确未通过，不借用日用会话冒充隔离环境。

**S-A03 资源清单。** 执行输入绑定项目、角色、工作区、资源版本和任务内容。资源记录来源、内容摘要、适用范围、是否必需；平台资产是权威，本地是落地副本。A 阶段用测试文件模拟中央下发，不预建资源服务。

**S-A04 准备先于启动。** 顺序为：验证目录及 Git 根 → 检查工作区与适用规则 → 解析所需资源 → 校验冲突及信任条件 → 准备文件并记录结果 → 启动 Codex。必需资源缺失、用户文件冲突或未满足信任条件时不启动。已有受管理文件被人工修改时报告差异，不静默覆盖。

验证目录与 Git 状态不是要求所有任务都在 clean tree 执行：只读任务可记录 dirty 状态；写任务应根据任务明确授权决定能否继续。冲突状态不隐式 stash/reset，不丢弃现有改动。

## 4. 协议和执行行为

**S-A05 协议基准。** 编码前根据选定可执行文件生成/核对协议结构，并对照官方资料确认初始化顺序、request/response/notification、审批和错误结构。记录协议来源与版本；不依据终端文本推测成功，不把其他版本的参数写成默认事实。

**S-A06 执行生命周期。** 候选方案为每次执行启动一个 app-server，通过 stdio 初始化、创建或恢复 thread、启动一个 turn、读取直到终态，再关闭本次子进程。一个 turn 可包含多轮模型和工具行为。响应按请求 ID 关联；读取事件时仍能发送审批响应及停止指令。

最少记录 execution ID、project ID、角色、工作区、资源摘要、进程实例标识和已获知的 thread/turn。线程恢复创建新执行记录并关联旧执行，不重用旧 execution ID 启动新工作。

**S-A07 状态真实。** 可观察事实包括已接收、准备中、执行中、等待人工、完成、失败、中断、结果待核对。状态字段的最终命名在实施计划确定；语义不能合并。进程存活或正常退出不独立证明任务完成，必须核对对应 turn 的终态。完成也不代表独立验证通过或用户验收。

**S-A08 事件。** 原始事件保留必要诊断，但秘密信息不能进入记录；输出文本可以合并，审批、错误和终态不能被普通文本合并丢失。事件绑定 execution ID 和单调序号，先可靠记录；未来中央接口沿用此归属，不在 A 阶段实现上传协议。

## 5. 审批、停止和副作用边界

**S-A09 原生权限审批。** 请求绑定 execution ID、进程实例、thread/turn 和原生 request ID，展示真实操作及可选决定。只对当前仍有效的请求回传用户选择；同决定重复提交不重复生效，冲突决定拒绝。完成、取消或进程重启后，旧请求不能应用到新执行。

此处只验证运行时权限，不实现 SOP 业务审批。后者属于阶段 D，绑定阶段或产物版本，并可独立于进程生命周期保存。

**S-A10 停止。** 首先请求中断对应 turn，观察最终结果；无法正常结束时只清理已识别的本次执行进程及其子进程。不能只凭 PID 杀进程，也不能影响其他测试执行或日用 Codex。中断超时及最终清理行为由所选协议与真实实验确定，并写入证据。

**S-A11 没有隐式授权。** 测试用无害且可观察的操作验证接受、拒绝和超时/失效；拒绝时目标副作用不存在。不改变全局权限策略来绕过审批。若测试环境根本未产生原生权限请求，该场景记未验证，不用 agent 文本询问代替。

## 6. 去重、占用和崩溃

**S-A12 执行去重。** 接收后先保存本地记录，再启动子进程。同一 execution ID、相同输入返回已有状态，不再启动；同 ID 不同输入拒绝且保留原记录。使用 sqlite3 标准库完成必要记录，不引入节点数据库服务。

**S-A13 工作区占用。** 相同规范化工作区同一时刻只接纳一个写任务；等待审批仍占用。另一个写任务返回可重试的繁忙结果，不启动。后续由中央排队，不在节点再造任务调度器。首轮以一个执行槽位验证，阶段 B/F 扩展并发时回归工作区约束。

**S-A14 未知窗口。** daemon 退出或电脑重启后，对未完成记录核对已知运行事实。已记录接收但无法证明是否启动、缺少 thread ID 或缺失终态，均不能据此自动重做。结果待核对是合法结果；只有显式恢复才能建立新执行。

**S-A15 恢复。** 新执行使用显式指定的原 thread 和一致的项目/角色归属，恢复前展示/记录工作区变更和未完成事实。协议无法证明的原命令执行情况保持未知，不声称恢复会话等于恢复系统命令。

**S-A16 写入故障。** SQLite 或事件文件无法写入时停止接收新任务；在途执行无法可靠记录时中断受影响任务，尽力输出不含秘密的诊断，不宣称任务完成。通过故障注入验证，不填满用户真实磁盘。容量阈值依据实际输出样本在后续部署规格确定，不在本规格虚构通用日志系统。

## 8. 验收结论与交付物

规格评审后，实施计划落实到 `runner/` 的协议、环境准备、执行记录、控制与测试文件，不预建后端或前端空工程。接口按实际协议证据确定，不将未核实的外部字段写成稳定契约。

本阶段交付：可测试的执行核心、模拟夹具、真实运行测试入口、资源来源与准备结果样本、版本与脱敏协议证据、逐场景结果，以及进入 B 所需的已验证行为清单。

报告注明时间、HEAD、Python/Codex/测试 runner 版本；按模拟测试、真实 Codex、进程运行时和静态检查分别给总计、通过、失败、跳过及未执行。逐文件计数及上述场景实测值必须可查。A 不部署中央容器，容器重建与 `--no-cache` 标为不适用。

通过标准：必需场景均有符合条件的证据；资源加载或隔离不成立时，先修改候选设计并重新验证。若所选 Codex 版本不支持需求中的能力，应明确提请需求调整，不能只删除失败测试后进入 B。
